나는 환경을 캐시하지 않고, recipe가 승인한 파생 바이트만 캐시했다.

Workshop을 새로 띄울 때마다, 또는 새 Bench가 같은 툴체인을 요구할 때마다 운영체제는 똑같은 ffmpeg를 다시 받고 다시 빌드했다. recipe로 깨끗하게 재현되는 빌드를 만들어 놓고서, 그 깨끗함을 매번 처음부터 다시 치르고 있었다. Bench 열 개가 전부 ffmpeg를 필요로 하면 다운로드도 열 번, 빌드도 열 번이다.

> "Ten Benches that all need ffmpeg means ten identical downloads and ten identical builds." — https://dev.to/constant_itis/ephemeral-shouldnt-mean-downloading-ffmpeg-again-3jgi

첫 반응은 Bench 전체를 스냅샷으로 캐시하는 것이었다. 그건 이미 버린 선택지다. 파일시스템 스냅샷은 잔여물과 비밀 값까지 통째로 담는다는 이유로 앞선 단계에서 이미 걷어냈다. 캐시할 대상을 환경째로 잡으면 같은 문제로 돌아간다.

## 세 가지를 분리한다

recipe, 파생 바이트, task state는 성질이 다르다. 섞어서 다루면 캐시가 권위를 갖는 사고가 난다.

| 대상 | 성질 |
|---|---|
| recipe | 진실의 원천. 선언적, 유일한 권위 |
| 파생 바이트 | 캐시. 유용하지만 버려도 되고, 권위 아님 |
| task state | 실행마다 버려지는 값 |

## Tool Shed: 입력의 해시로 이름을 붙인다

캐시에 이름을 줬다. Tool Shed. 여기 저장되는 파일은 하는 일이 아니라 무엇으로 만들어졌는가로 이름 붙는다. 키는 recipe가 승인한 입력의 해시다. 어떤 sealed base에서 파생됐는지, 버전까지 고정된 패키지 집합이 무엇인지, 파생 과정에 허용된 네트워크 프로필이 무엇인지가 전부 키에 들어간다. 입력이 같으면 키가 같고, 키가 같으면 바이트가 같다.

ffmpeg는 한 번만 빌드된다. 같은 derivation을 선언한 모든 Bench와 Workshop이 그 캐시된 산출물을 그대로 재사용한다. Agent는 이 과정에 관여하지 않는다. 실행 시점에 운영체제가 recipe로부터 키를 계산하고 Tool Shed를 조회한다. 있으면 재사용하고, 없으면 recipe로 다시 파생시켜 저장한 뒤 완성된 환경을 넘긴다. Agent 입장에서는 둘 다 똑같이 준비된 Bench를 받을 뿐이다. 한 번 캐시된 derivation은 네트워크 없이도 재현된다. ephemeral은 이제 "ffmpeg를 또 받는다"가 아니라 task state만 버려진다는 뜻으로 돌아간다.

## 스냅샷과 다른 점은 방향이다

Tool Shed도 결국 저장된 산출물이니 스냅샷처럼 들릴 수 있다. 다른 건 방향과 권위다. 스냅샷은 그 자체가 진실이었다. 신뢰해야 하는 불투명한 덩어리였다. Tool Shed는 recipe로부터 파생된다. 권위는 여전히 recipe에 있다. 캐시 미스는 사건이 아니다. 운영체제가 recipe로 다시 파생시킬 뿐이다. Tool Shed 전체를 지워도 잃는 건 시간뿐이다. 이건 순수한 최적화이지, 시스템이 독립적으로 신뢰하는 대상이 아니다. supervisor는 Tool Shed 안의 모든 바이트가 검증된 recipe 실행에서 나왔는지 확인한다. Tool Shed에게 "뭐가 안전한지"를 묻지 않는다. "뭐가 존재하는지"만 묻는다. 안전은 recipe가 책임진다.

이 아이디어 자체는 새로 만든 게 아니다. Nix store는 산출물을 입력으로 키를 매긴다. Bazel도 빌드 액션을 같은 방식으로 캐시한다. OCI 레이어는 콘텐츠 주소 방식으로 공유된다. 패키지 매니저는 전부 다운로드 캐시를 갖고 있다. 수십 년 된 아이디어를 recipe 생애주기에 맞춰 끼운 것뿐이다.

## 안 한 것: 해시를 신뢰의 증거로 쓰지 않는다

해시가 기대한 값과 맞으면 믿어도 되는가. 아니다. 해시는 신원이지 안전이 아니다. SHA-256은 악성코드도 정확하게 식별한다. derivation 도중 apt 패키지를 내려받았다면 해시는 그 패키지를 포함해 계산된다. 네트워크가 오염됐거나 패키지 인덱스가 오염됐어도 해시는 여전히 맞다. 오염된 데이터에 대해 맞는 것뿐이다. Tool Shed는 그 오염된 데이터를 이후 그걸 요구하는 모든 Bench에 그대로 내준다. 빠르고 일관되지만, 안전하지는 않다.

이 글은 신뢰 문제를 풀지 않는다. 빌드 도중 민감한 파일을 볼 수 있는 환경에서 만들어진 파생 바이트가 여러 Bench에 재사용될 때 생기는 프라이버시 문제도 풀지 않는다. "해시가 맞는다"가 "안전하다"로 승격되는 지점을 막는 방법은 아직 없다.

> recipe는 진실, 파생 바이트는 버려도 되는 캐시, task state는 매번 버려진다. 해시는 신원을 증명할 뿐 안전을 증명하지 않는다.
